# Sentinel Controlled Remediation Security Model

## 1. Separation of Duties & Authorization
- **Triage Proposal:** Generated by `triage.Processor` with `Tools: nil` (no execution capability).
- **Human Approval (`incidents:approve`):** Only an authenticated human principal in the owning tenant can transition `pending_review` $\rightarrow$ `approved`.
- **Execution (`incidents:execute`):** `POST /v1/incidents/{id}/remediate` requires `incidents:execute` scope and derives `tenant_id` exclusively from `auth.Principal`.

## 2. 9-Step Execution Authorization Boundary
1. Validate `ActionRequest` (`ActionVersion == "1.0.0"`, allowlisted `ActionType`, safe parameter keys/values, no shell/SQL/URL characters).
2. Load persisted `TriageView` scoped by `tenant_id`.
3. Enforce `triage.CanExecuteAction` (must be `approved`, non-empty `DecidedBy`, not expired).
4. Verify `req.ApprovalID == view.Approval.ID`.
5. Enforce `ActionMatchesApprovedRecommendation` (e.g., `route_failover` only authorizes `switch_payment_route_to_backup`).
6. Acquire atomic `ClaimExecution` lock (`FOR UPDATE` + `execution_token`).
7. Apply action to isolated `remediation.Simulator` (zero network/cloud/DB side effects).
8. Run `VerifyPostAction` against authoritative simulator snapshot.
9. Persist outcome fenced by `execution_token`.

## 3. Independent Post-Action Verification
`VerifyPostAction` inspects `before` and `after` `Snapshot` values directly and separates `RecommendationValid`, `ApprovalValid`, `ExecutionSucceeded`, `VerificationPassed`, and `SafetyPassed`.
